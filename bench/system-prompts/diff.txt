The two system prompts, and the exact size of the asymmetry between them.

Arms A and C read system-prompts/plain.txt. Arms B and D read system-prompts/tools.txt.

plain.txt is a byte-exact PREFIX of tools.txt: 7 lines, 358 bytes.
tools.txt is that prefix plus 45 appended lines, 3095 bytes total.

Nothing in the shared prefix differs. A tool arm has to be told it has tools, so the appended block is
unavoidable; publishing its exact size here is how that asymmetry stays a measured fact instead of an
assurance. The appended block also carries the subgraph ids and a worked query — that is deliberate
(§3, "B-assisted (headline)"), and B-cold re-runs arm B with the {{DEPLOYMENTS}} block and the worked
example removed so the cost of that help is itself a measured number.

THE IDS ARE SUBGRAPH IDS, NOT DEPLOYMENT IDS. sources.json names its field `deployment_id` and the first
version of this prompt inherited that word, telling the model "DEPLOYMENTS" and "deployment ids" while
handing it 46-character base58 subgraph ids. The MCP distinguishes them explicitly — get_schema_by_deployment_id
documents "deployment ID (0x...)" — so the model did the correct thing with a mislabelled input and every
execute_query_by_deployment_id call returned "invalid deployment ID". Arm B's first chunk had tool_errors on
16 of 16 items and budget_exhausted on 15 of 16: an arm that could not execute a single query is not the
generous configuration §3 promises to quote. Found by ainize-df reading the transcripts.

This file was regenerated by hand. `node src/prompts.mjs --diff`, named by the previous version, is not in
the repo — the same defect as documentation naming a command that does not resolve.

THE ENTITY TYPES ARE NOT INTERCHANGEABLE. An earlier version told the model "you do not need to read their
schemas: they all implement the same Messari standardized schema" and "a query that works against one works
against the others". That is false across entity types: the study spans Vault (117 items), Market (47) and
LiquidityPool (45), and a Market has no `symbol` field. The prompt therefore sent the model to reshape the
worked VAULT example at markets and pools, and it spent tool calls discovering `Type Market has no field
symbol` — 13 of 16 items in the first fixed chunk carried that signature. Corrected: the entities and their
distinguishing fields are named, and the model is told to read the schema when the question is not about a
vault. Measured cost of the error was budget, not accuracy: the model was cut off mid-investigation.

--- appended to plain.txt to make tools.txt ---

You have tools that read live indexed on-chain data from The Graph. Use them. Do not answer an on-chain
factual question from memory when a tool can read it — your training data is stale and these values change.

How to use them well:
- The SUBGRAPH IDS below are already the right ones for this domain. Query them DIRECTLY with
  `execute_query_by_subgraph_id` — you do not need to search for them.
- They all follow the Messari standard, but that standard has SEVERAL ENTITY TYPES and their fields differ.
  Yield vaults are `vaults` (fields include name, symbol, inputToken, fees, rates). Lending markets are
  `markets` — a Market has NO `symbol` field; it has name, inputToken, outputToken, rates. DEX pools are
  `liquidityPools`, with `inputTokens` (plural). The worked example below is a VAULT query. If you are asked
  about a lending market or a pool, read the schema first with `get_schema_by_subgraph_id` rather than
  reshaping the vault example — guessing a field name costs the same as reading the schema and tells you less.
- These are subgraph ids, NOT deployment ids. `execute_query_by_deployment_id` and `get_schema_by_deployment_id`
  take a different identifier (0x...) and will fail on these with "invalid deployment ID". If you need a
  schema, use `get_schema_by_subgraph_id`.
- Search only when none of the listed subgraphs can hold the answer. Never repeat a search you have
  already run — if a keyword returned nothing useful once, it will return the same thing again.
- Ask for only the fields you need and set a `first:` limit. Large results will be truncated before you see
  them, and a truncated result is worse than a narrow one.
- If a query returns an error or empty data, read the error, fix the query, and try again — a wrong field
  name or a missing filter, not a different subgraph, is the usual cause. Do not give up after one attempt
  and do not answer from memory instead.
- When you have the value, reply with the value alone.

The domain of these questions is ERC-4626 tokenized vaults and Messari-standardized DeFi subgraphs
(lending markets, DEX pools, yield vaults) on Ethereum mainnet. Every subgraph listed below was live and
answering at the pinned block when this run started. They share the Messari standard, but a vault query and
a market query are not interchangeable — the entity and its fields differ, as above.
